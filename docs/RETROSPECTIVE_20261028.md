# Day104 振り返り・次回AIへの引継ぎ
2026年10月28日（日本時間）／ANGEL BOUNCE

## 結論
最大の失敗は、スマホで遊ぶ作品なのに、実機での起動・処理負荷を確かめる前に、PC/Editor上で機能と演出を作り込んだこと。公開成功とスマホで遊べることは別の完成条件にする。

## 成果と確認範囲
- Unity版に投球・反射・受取・成功/失敗、タッチ/ゲームパッド、BGM、美術とエンディングを実装。Editor検証・iOS書出しの過去記録がある。
- Web公開後、ユーザーから「携帯で異常に重くプレイできない」と報告。実機性能は未検証だった。
- 公開データとwasmは計67,734,792バイト。スマホのdevicePixelRatioを制限していなかった。DPR=3では同一CSS面積に対して描画画素が9倍になる。これらは確認できた負荷要因であり、実機プロファイルなしに唯一の原因とは断定しない。
- スマホはDPR<=1・描画長辺<=960pxに修正。gzipの2ファイルは計36,430,737バイトで、通信対象サイズを46.2%削減。展開後のメモリとfpsが46.2%改善した意味ではない。
- 圧縮版はgh-pages `ecaf0f8b623fe63a73ffdd83686150384f58ede0`。GitHub上のHTMLを読み直して圧縮処理を確認し、ファイルサイズとPages配信ジョブ `40692039297` のsuccessを確認。公開HTTPのハッシュ照合と更新後の実プレイは未確認。
- JS構文、スマホ縦横/タブレット/PCの解像度上限、gzip展開、wasm MIME、通信失敗時/非対応ブラウザの元ファイルfallbackをNodeで検証。ローカルgzipは展開後完全一致。

## 失敗・原因・次回の強制手順
| 失敗または手戻り | 判断の問題 | 次回AIが行うこと |
| --- | --- | --- |
| スマホで遊べない状態を公開 | PC/Editorでの成功をスマホ品質へ広げて解釈 | 遊びの核が動いた時点で実機起動を確認。実機がなければNOT_TESTEDとし、完成報告で明示 |
| 約65MiBを無圧縮で配信 | 公開の簡便さとGitHubの上限を、モバイル性能の基準にしてしまった | 配信量・起動時間・定常fpsを別に確認。モバイルDPRと描画上限を初期設定にする |
| 機能・美術・音・演出まで先に拡大 | 基本プレイと対象端末の確認が後回し | 投げる→反射→届く→再挑戦を通してから演出を追加 |
| ローカル配信の起動失敗に気づく前にブラウザを開いた | サーバー起動コマンドが返した継続IDを、待受成功と取り違えた | 先にプロセス出力とHTTP応答を確認してからブラウザを開く。バインド拒否なら即別経路へ |
| ブラウザ接続で長時間停止 | 利用できない検証経路に依存 | 初回接続失敗を具体的に記録し、ソース検証と公開ジョブ確認へ切替。繰り返し待たない |
| 追加のActionsデプロイが失敗 | 既存のgh-pages公開と別のenvironmentを重複使用 | 既存Pagesのブランチ配信を利用。不要な追加デプロイjobを除去し、生成と公開成功を別に読む |
| 検証件数が文書間で39/45と不一致 | 証拠と対象コード版の結び付けが弱い | 件数だけで合格としない。対象コード、日時、検証種別を残し、変更後は関連検証を再実行 |
| shellからGitHubへ接続不可 | ツールの可用性を事前確認していない | 使えるGitHubコネクタを優先。保存後は内容を読み戻す。ローカルgitとリモートを同期済みと推測しない |
